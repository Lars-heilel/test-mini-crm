# Решения и допущения

Документ фиксирует, что именно реализовано и какие трактовки выбраны там, где ТЗ
допускало варианты. Полная спецификация — в
[`specs/001-mini-crm-objects-tasks/spec.md`](../specs/001-mini-crm-objects-tasks/spec.md).

## Продуктовые решения

- **A-001. Одна роль на пользователя.** Роли «постановщик» и «исполнитель»
  взаимоисключающие. Совмещение не поддерживается.
- **A-002. Мягкое удаление.** У объектов и задач есть `is_deleted`. Запись скрыта,
  если удалена сама или удалён её объект. Каскадных триггеров нет: видимость
  ограничивается политиками и helper-функциями. `task_history` не удаляется.
- **A-003. Описание необязательно.** Обязательны название, объект и исполнитель.
- **A-004. Редактирование задачи.** Постановщик меняет название, описание, объект и
  исполнителя в любом статусе, кроме удалённой задачи. Статус меняется только
  разрешёнными переходами. Изменения полей не пишутся в историю: история — только
  смены статусов.
- **A-005. Создание в истории.** Первая запись — «Создание → Новая».
- **A-006. Комментарий к доработке.** Обязателен только для перехода
  «На проверке» → «На доработке», максимум 2000 символов.
- **A-007. Удаление объекта.** Скрывает объект и все его задачи; история остаётся.
- **A-008. Пользователи вне приложения.** Аккаунты и роли создаются вручную
  (в демо — сидом). Экрана администрирования нет.
- **A-009. Без восстановления пароля и подтверждения email.** Это вне MVP.
- **A-010. Стартовый экран.** Постановщик попадает на `/objects`, исполнитель — на
  `/my-tasks`. Раздел «Мои задачи» постановщику недоступен.
- **A-011. Минимальные списки.** Поиск, фильтры и пагинация не требуются; задачи
  сортируются от новых к старым.
- **A-012. Русский интерфейс.** Desktop-first с базовой адаптацией.
- **A-013. Серверные дата и автор.** Клиент не передаёт и не меняет автора/время
  истории.
- **A-014. Удалённые записи не видны никому**, включая постановщика, но остаются в
  базе.
- **A-015. Переназначение задачи** не создаёт запись в истории статусов: новый
  исполнитель сразу получает доступ, прежний теряет.

## Технические решения

- **shadcn/ui вместо самодельных компонентов.** Кнопки, карточки, диалоги, поля и
  бейджи взяты готовыми; кастомные обёртки — только над shadcn
  (`ObjectFormModal`, `TaskFormModal`, `ConfirmDialog`, `StatusBadge`).
- **Безопасность на уровне БД.** RLS включён на всех четырёх таблицах. У
  `authenticated` нет `UPDATE`-права на `tasks.status`, `author_id`, `created_at`.
  Прямой `UPDATE` статуса возвращает ошибку.
- **Единая точка смены статуса.** RPC `change_task_status(...)` с
  `SECURITY DEFINER` проверяет роль, назначение, матрицу переходов и комментарий,
  блокирует задачу `FOR UPDATE` и атомарно пишет историю. Два одновременных запроса
  дают один успешный переход и одну запись истории.
- **История только для чтения.** У `task_history` есть только `SELECT`-права.
  `INSERT` делают триггер создания и RPC; `UPDATE`/`DELETE` запрещены даже
  постановщику.
- **Профили.** Авторизованные читают только `id`, `full_name`, `role`; роль нельзя
  изменить через API.
- **Исправление RETURNING.** Отдельная миграция
  `20261105120200_fix_returning_visibility.sql` меняет SELECT-политики так, чтобы
  `INSERT ... RETURNING` не упирался в helper, перезапрашивающий ту же таблицу.
- **Проверки.** `npm test` — чистая матрица действий; `npm run verify:security` —
  16 интеграционных проверок RLS и RPC на живом Supabase.

## Что не входит в демо-версию

- регистрация, восстановление пароля, подтверждение email, смена пароля;
- экран управления пользователями и ролями;
- уведомления (email, push, в приложении), real-time;
- комментарии/обсуждения внутри задачи, кроме комментария к смене статуса;
- вложения, фотографии, чек-листы, дедлайны, приоритеты, теги, бюджет;
- несколько компаний/арендаторов, интеграции, импорт/экспорт;
- журналирование изменений полей задачи;
- мобильное приложение, офлайн-режим, другие языки;
- нагрузочное тестирование и промышленный мониторинг.
